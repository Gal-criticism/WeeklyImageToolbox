# SQLite 持久化实施记录

范围：任务状态集中进入 SQLite，原图和审阅图仍为文件，final 不由迁移修改。

## 实施步骤

- [x] TaskRepository：版本化结构、增量事务、版本化决定、相对路径、完整性与备份
- [x] 旧任务迁移：校验、隔离损坏批次、可继续、完成后切换
- [x] 流水线：检查点、下载日志、X 缓存与补抓接入
- [x] 审核：数据库读取、后台决定保存、分页与最新人工决定保留
- [x] 资产：任务内哈希原件和审阅件复用
- [x] 工具箱迁移按钮；CLI 迁移、检查、整任务备份入口
- [x] 离线回归、实际任务副本及 3000 候选基准

实施决定：新任务使用 SQLite；旧任务显式迁移前继续使用原 JSON 链路。
发布时可产生兼容 JSON 快照，日常下载与审核不再双写 JSON。
既有输出删除保持不动；不调用付费 API，不修改筛选或视频规则。

## 验证记录

Windows、Python 3.13.9、SQLite 3.51.0；使用 DELETE 日志与 FULL 同步，未启用 WAL。
结果汇总见 [sqlite-validation.json](sqlite-validation.json)。

实际任务仅在独立副本上迁移，副本结束后清理；正式任务仍保持旧格式。
1862 个图片候选、56 个视频候选、3627 条失败记录、1918 项审核决定和 22 条新闻的来源记录核对一致。
路径按任务内相对位置归一后，89376 个原有图片字段的比较没有差异。
原任务与副本的 51 个 JSON 文件、430 个 final 文件清单及 SHA-256 均未改变。
迁移后资产完整性检查通过。

3000 候选、50 条新闻的固定合成样本：

| 操作 | 耗时 | Python 分配峰值 | 进程工作集采样峰值 |
| --- | ---: | ---: | ---: |
| JSON 全量写入 | 24.3 ms | 821 KiB | 67.7 MiB |
| SQLite 首次插入 | 257.7 ms | 79 KiB | 72.1 MiB |
| SQLite 更新 10 条 | 9.0 ms | 12 KiB | 72.2 MiB |
| JSON 读取并筛选 100 次（每次返回最多 100 项） | 1116.8 ms | 3.41 MiB | 75.9 MiB |
| SQLite 筛选 100 次（每次返回最多 100 项） | 220.3 ms | 82 KiB | 72.4 MiB |

首次入库比一次小型 JSON 写入更慢；优势在增量保存和按条件读取。
工作集每 5 ms 采样，包含进程已有分配，不等同于任务净占用或爬取全过程峰值。
审核快照仍保留候选对象及当前人工决定；后台从数据库按新闻分批读取 ID，最多 100 项，避免重读完整候选 JSON 覆盖最新决定。

回归覆盖迁移中断与重复执行、损坏批次隔离、旧数据兼容、目录移动、离线补抓、版本冲突、锁等待、事务回滚、落盘中断恢复及不支持硬链接的文件系统。
SQLite 外部独占锁约 5 秒后报告错误，释放后可以继续保存。

完整回归：763 passed、4 skipped（其中新增符号链接迁移测试在当前 Windows 权限下跳过）。
导入任务迁移也会纳入私有审核决定、任务选项及补抓资产；批次候选按归属和路径校验，
有效文件复制到源任务的哈希资产目录，旧文件不删除。重复迁移不覆盖权威库中的决定。

源码已接入工具箱和 CLI；本轮没有重新构建或发布便携 EXE。
